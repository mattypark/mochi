# How Grammarly actually works

Research notes for generalising mochi from a Substack pet into a writing assistant
that works anywhere. Primary sources throughout — engineering blog posts, shipping
extension code, specs, and issue threads. Marketing pages are not cited. Anything
that could not be confirmed is in **Open questions** at the end rather than guessed at.

One note on provenance: several claims below come from unpacking the live
**Grammarly for Chrome CRX v14.1322.0** (extension ID `kbfnbcaeplbcioakkpcpgfkobkghlhen`).
Those are shipping code, not inference, and are marked as such.

---

## 1. Architecture — how the extension gets into a page

### 1.1 It attaches on focus, not by scanning

The manifest is MV3, `host_permissions: ["http://*/*","https://*/*"]`, with **eight**
content-script blocks. There are two tiers: a light `Grammarly-check.js` injected
almost everywhere (with 91 `exclude_matches`), and a heavy `Grammarly.js` added back
on roughly 90 hand-listed hosts — Gmail, Slack, LinkedIn, X, Teams, Jira. Everything
is `run_at: document_idle` except Google Docs, Overleaf and Office, which are
`document_start`. `all_frames: true` and `match_about_blank: true` are set.

The discovery core, verbatim from `Grammarly.js` module `21208`:

```js
const t = k.V.create("universal.cs.integration.observables"),
      n = e => (0,o.R)(e, "focus", {capture: true});
function i(e){
  return e instanceof Element && e.shadowRoot && e.shadowRoot.activeElement
    ? i(e.shadowRoot.activeElement) : e
}
```

So the primary trigger is a **capture-phase `focus` listener on the document** (not
`focusin`), plus an initial `document.activeElement` poll. `composedPath()[0]` is used
in place of `event.target` so shadow DOM is pierced, with recursive
`shadowRoot.activeElement` descent.

There *is* a document-wide `MutationObserver({childList, subtree})` (module `56113`),
but it is **not** a general editable-scanner. Its jobs are discovering new `<iframe>`
nodes and driving a selector-based read-only integration. Same-origin iframes get the
whole pipeline re-run inside them once `contentDocument.readyState === "complete"`.
Cross-origin iframes are impossible and are not attempted.

This matters for mochi: **mochi currently observes `document.body` with a subtree
MutationObserver and re-resolves the editor every tick.** That is fine for one known
site. It does not generalise — on a heavy page it is exactly the cost profile Grammarly
avoided.

Because there is no event for "this element moved", the textarea integration also runs
**polling clocks**: `C.z.hz4` (value, 4 Hz), `C.z.sec1` (style, 1 s), `C.z.hz10`
(style recalc, 10 Hz). This is the shipped form of the blog's complaint that
"there is no API or event to know when these values change."

**Eligibility gates** (module `36115`):

```js
this.MIN_INIT_REQUIRED_FIELD_HEIGHT = 35,
this.MIN_INIT_REQUIRED_FIELD_WIDTH  = 250
```

`<input>` is **never** integrated — contenteditable and textarea only. And `dir="rtl"`
is treated exactly like an opt-out attribute: **Grammarly refuses RTL fields outright.**

### 1.2 What it injects

Element and attribute names are generated by module `59818` as `` `grammarly-${e}` ``
and `` `data-grammarly-${e}` ``.

- `<grammarly-extension>` — per-field host, carrying `data-grammarly-part="highlights"`
  or `="button"`.
- `data-grammarly-shadow-root="true"` — the "this subtree isn't yours" marker.
- `<grammarly-desktop-integration>` — **not** the underline layer. A visually hidden
  (`clip:rect(0,0,0,0)`) shadow-rooted div on `document.documentElement` with
  `role="group"` and `aria-label="grammarly-integration"`, whose state is written as
  `data-content` JSON and surfaced via `content: attr(data-content)` so the *desktop
  app* (which reads pages through accessibility APIs) can see extension state. This is
  why it leaks into copy-pasted text.
- `<grammarly-mirror>` / `data-grammarly-part="mirror"` — the hidden mirror for
  `<textarea>`, re-rendering `value` split into **1000-char text nodes**
  (`this._textNodeSize = 1000`) so `Range.getClientRects()` can run against text a
  textarea will not otherwise expose.

Worth correcting a widespread belief: **`data-new-gr-c-s-check-loaded` and
`data-gr-ext-installed` do not appear anywhere in v14.1322.0.** A grep finds only
`data-gr-wac-build`. These are legacy markers, even though the entire Next.js
hydration-warning ecosystem still names them.

### 1.3 The opt-out table (shipping code)

This is the definitive answer to the `data-gramm` folklore. Module `61379`:

```js

         {name:"aria-label",            value:"Search Facebook"}],

    l = {name: i, value: "true"}

```

Reading it out:

- `data-gramm`, `data-gramm_editor`, `data-gramm_id`, `gramm_editor` are matched by
  **presence only** (`e.hasAttribute(t)`). So **`data-gramm="true"` disables Grammarly
  exactly as hard as `data-gramm="false"`.** Confirmed independently in
  [slate#2855](https://github.com/ianstormtaylor/slate/pull/2855): "the extension
  doesn't seem to work as long as the prop `data-gramm` exists irrespective of its value."
- `data-enable-grammarly` is value-matched, and `"true"` is the **override** that beats
  every blocklist entry.
- **`class` is substring-matched against `"ProseMirror"`.** Every stock ProseMirror
  editable — and TipTap's, which ships `class="tiptap ProseMirror"` — is blocklisted by
  class name. Also `pm-container` and `data-synchrony` (Confluence's collab layer).
- `data-slate-editor` is **gone** from the table; that interference is resolved.
- Grammarly has **never documented any of this**. The
  [official integration page](https://support.grammarly.com/hc/en-us/articles/10139846131213-How-do-I-integrate-Grammarly-with-my-website-or-application)
  never mentions `data-gramm`. All folklore traces back to
  [slate#733](https://github.com/ianstormtaylor/slate/issues/733).

The direct consequence for mochi: **Substack's editor carries `class="tiptap ProseMirror"`,
so Grammarly opts itself out of the exact surface mochi targets.** That is a real
positioning gap, not a technicality.

### 1.4 Why they abandoned DOM injection

Source: [Making Grammarly Feel Native On Every Website](https://www.grammarly.com/blog/engineering/making-grammarly-feel-native-on-every-website/),
Serhii Yavnyi. The old DOM looked like this:

```html
<div contenteditable="true" data-gramm_id="d1a428f0-40fd-..." data-gramm="true"
     spellcheck="false" data-gramm_editor="true">
  That <g class="gr_ gr_4 gr-alert gr_spell gr_inline_cards gr_run_anim
                 ContextualSpelling ins-del" id="4" data-gr-id="4">its</g>
  when I decided <g class="...Grammar multiReplace" id="3">getting</g> on the bike.
</div>
```

Two reasons are given, both quoted:

> "First, by mixing text and underlines, **we pollute the text field content**. The text
> field is supposed to only contain actual text, and most of the code running on the web
> expects that to be the case—and rightly so. If Grammarly doesn't remove the extraneous
> underline nodes before the website's code can notice them, it can **corrupt the user's
> text, crash the website's code, or make an email include underlines when it gets
> sent**. Yikes. And most of the time, there's no way to know when precisely the
> underlines should be removed."

> "Another—perhaps even bigger—issue … is that **websites don't like it when somebody
> tries to change their DOM**. The code running on the site expects that the DOM it
> created will not be changed by any other code. If that assumption is broken, bad
> things can happen. So both website and text editor developers started to look for ways
> to disable Grammarly, including such popular editors as **ProseMirror, Quill.js,
> Draft.js**, and many others."

The replacement, quoted:

> "Note how the underline elements container is the **very last element of the document
> body**. Each underline is positioned to be exactly on top of a corresponding text
> fragment."

```html
<body>
  <div contenteditable="true" spellcheck="false"> That its when I decided getting on the bike. </div>
  <highlights>
    <div>
      <div style="position: fixed; top:31px; left:47px;  width:15px; height:3px; background:rgba(255,0,0,0.5);" />
      <div style="position: fixed; top:31px; left:168px; width:45px; height:3px; background:rgba(255,0,0,0.5);" />
    </div>
  </highlights>
</body>
```

The prototype is described as "under 200 LoC, including all of the boilerplate."

**mochi already got this right.** `content.js` says so in a comment — "Nothing is ever
inserted into the editor: ProseMirror owns that subtree and treats foreign nodes as
document content." That decision is correct and is the one thing that does not need to
change.

### 1.6 The official SDK is dead

`@grammarly/editor-sdk` — first published 2021-04-22, last version `2.5.5` on
2023-10-20, now carrying npm's `deprecated: "Package no longer supported."` Sunset
announced 2023-07-12, shut down **2024-01-10**
([TechCrunch](https://techcrunch.com/2023/07/13/grammarly-to-shut-down-the-text-editor-sdk-in-january/)).
`grammarly/grammarly-for-developers` now 404s.

There was **never** a ProseMirror or CodeMirror package — both 404 on the registry, so
that common claim is false. Architecturally the SDK mattered because you placed
`<grammarly-editor-plugin>` yourself (so the host owned stacking and scroll context)
and suggestions applied **through the editor's transaction model**. Its death means
there is now **no sanctioned integration path at all**.

### 1.7 Overlay vs inline decoration — the tradeoff

| Dimension | Inline marks (PM `Decoration.inline` / CM6 `Decoration.mark`) | Absolute overlay |
|---|---|---|
| Text geometry | Free and exact — wrapping, ligatures, bidi are the browser's problem | Recompute rects; one logical range → **N rects** |
| z-index / stacking | Immune | Central hazard. Grammarly copies the editor's `z-index` onto the overlay root and inserts as a sibling. Blog: the field "can be covered by an element with `position: sticky`" |
| Scroll sync | Free | Every scrollable ancestor + `visualViewport`; nothing fires on layout shift → hence the 1 s / 10 Hz polling |
| Ancestor transforms | Free | Grammarly **regex-parses `scale()`/`matrix()`** from computed transform and applies `scale(1/x, 1/y)` plus a compensating translate. Rotation and 3D are **not** handled |
| iframes | Free | Per-frame injection + same-origin checks; cross-origin impossible |
| Shadow DOM | Free | Needs `composedPath()`, recursive `shadowRoot.activeElement`, per-root style injection |
| Virtualised editors | Cheap — CM6 computes decorations *after* the viewport is known | `getClientRects()` on unrendered content returns nothing |
| RTL / bidi | Browser handles it | Genuinely hard — almost certainly why Grammarly **refuses `dir="rtl"`** |
| Line wrapping | CM6: "line breaks always end decoration elements" | One rect per line box, by hand |
| Layout influence | Marks can change wrapping | The whole point: overlay layers "don't take up space and shouldn't influence line wrapping" |
| Accessibility | Inherited | Lost. CM6: layer content is "invisible to screen readers." Grammarly's answer is the hidden `<grammarly-desktop-integration>` ARIA bridge |
| Hit testing | Free | `pointerEvents:"none"` overlay with selective re-enable; adds cost to the host page |

The honest summary: **inline decoration is strictly better when you own the editor, and
strictly impossible when you don't.** A universal assistant has no choice but overlay.
CM6's `layer({above, class, markers})` + `RectangleMarker(className, left, top, width, height)`
is the blessed overlay primitive if you ever do own the editor.

## 2. The hard part — character offset N → pixel rectangle

This is the core problem, and it has three distinct solutions depending on the surface.

### 2.1 Why the rects are plural

[CSSOM View §9](https://drafts.csswg.org/cssom-view/#extensions-to-the-range-interface),
verbatim:

> For each `Text` node selected or partially selected by the range … include scaled
> `DOMRect` object (**for the part that is selected, not the whole line box**). The
> bounds … are computed using **font metrics**; thus, for horizontal writing, the
> vertical dimension of each box is determined by the **font ascent and descent**, and
> the horizontal dimension by the **text advance width**. If the range covers a partial
> typographic character unit … **the full typographic character unit must be included**.
> … **The transforms that apply to the ancestors are applied.**

Three independent sources of multiplicity:

1. **Line wrapping** — one rect per line fragment.
2. **Inline element boundaries** — each element fully inside the range whose parent
   isn't contributes its own **border area** rect. So `<em>`, `<code>`, `<img>` add fat
   padding+border boxes, not advance boxes.
3. **Bidi runs** — logically contiguous, visually discontiguous.

Note the vertical dimension is **font ascent + descent, not `line-height`** — a naive
underline drawn at `rect.bottom` sits tighter than the line box.

**The `getBoundingClientRect()` trap**, from the same spec: step 3 says if all rects have
zero width or height, return the *first*; step 4 unions only rects "of which the height
or width is not zero." So **zero-width rects are excluded from the union**, and the
bounding rect can fail to contain its own client rects. And an empty list returns
`{0,0,0,0}` — indistinguishable from "at the origin."

**Rule: `rects.length === 0` means "not rendered", never "at 0,0."** Return `null`.

### 2.2 contenteditable — offset → (textNode, offset) → Range

The canonical technique is `document.createTreeWalker(root, NodeFilter.SHOW_TEXT)`,
accumulating `node.length` until you cross the target offset.

The correctness landmine is **which plain text you indexed**. `textContent` (what a
TreeWalker reproduces) ≠ `innerText` (layout-dependent, collapses whitespace, turns
`<br>` and block boundaries into `\n`). If your offsets came from what the user visually
sees, a raw `textContent` walk drifts.

Harper handles this explicitly, in
[`domUtils.ts`](https://github.com/Automattic/harper/blob/master/packages/lint-framework/src/lint/domUtils.ts):

```ts
/** Accounts for `<br>` elements which `innerText` converts to newlines. */
export function getRangeForTextSpan(target: Element, span: Span): Range | null {
	const children = leafNodes(target);
	const range = document.createRange();
	let traversed = 0, startFound = false;
	for (let i = 0; i < children.length; i++) {
		const child = children[i] as HTMLElement;
		if (child.nodeName === 'BR') { traversed += 1; continue; }   // <br> counts as one char
		const childText = child.textContent ?? '';
		if (traversed + childText.length > span.start && !startFound) {
			range.setStart(child, span.start - traversed); startFound = true;
		}
		if (startFound && traversed + childText.length >= span.end) {
			range.setEnd(child, span.end - traversed); return range;
		}
		traversed += childText?.length ?? 0;
	}
	return null;
}
```

It also keeps a module-scope `sharedRange` to avoid a per-measurement allocation.

**CodeMirror 5** adds two tricks worth stealing, from
[`position_measurement.js`](https://github.com/codemirror/codemirror5/blob/master/src/measurement/position_measurement.js):

```js
for (let i = 0; i < 4; i++) { // Retry a maximum of 4 times when nonsense rectangles are returned
  while (start && isExtendingChar(...)) --start          // expand over combining chars first
  ...
  rect = getUsefulRect(range(node, start, end).getClientRects(), bias)
  if (rect.left || rect.right || start == 0) break       // all-zero rect = retry, not "at 0,0"
  end = start; start = start - 1; collapse = "right"
}
```

and it detects wrap points from the rect list itself, with a 2px tolerance:

```js
if (Math.abs(cur.bottom - next.bottom) > 2) heights.push((cur.bottom + next.top) / 2 - rect.top)
```

### 2.3 rangefix — the browser bugs you will hit

[rangefix](https://github.com/edg2s/rangefix) documents exactly which engines lie:
Chrome ≤54 returns rects for all parents of `endContainer`; Chrome 55 drops the rect for
wrapped images; Safari and Firefox have variants near block/inline edges; and **both**
Chrome and Firefox produce a bounding rect that doesn't cover all individual rects when
a selection spans a space across two lines.

It **feature-detects at runtime and never UA-sniffs**:

```js
broken.getClientRects = broken.getBoundingClientRect = range.getClientRects().length > 1;
...
// Safari doesn't return a valid bounding rect for collapsed ranges
broken.getBoundingClientRect = boundingRect.top === 0 && boundingRect.left === 0;
```

Two pieces worth taking even without the library: it returns **`null`** (not a zero
rect) for an empty list, and `batchPush` batches at 1024 because spreading a long
`DOMRectList` into `Array.push` blows the argument limit.

### 2.4 Mirror div — for `<textarea>` and `<input>`

**Why you must.** The value of a text control is not in the document tree.
`textarea.firstChild` is the *default value* node (stale once the dirty-value flag
flips); `<input>` has no children at all. The live text lives in a **closed UA shadow
tree** (`TextControlInnerEditorElement` in Chromium, visible only with "Show user agent
shadow DOM"). A direct corollary: **the CSS Custom Highlight API cannot highlight inside
a textarea**, because `Highlight` takes `Range`s and there are none to be had.

**`component/textarea-caret-position`** copies **28 CSS properties**:

```js
var properties = [
  'direction',  // RTL support
  'boxSizing',
  'width',  // on Chrome and IE, exclude the scrollbar, so the mirror div wraps exactly as the textarea does
  'height', 'overflowX', 'overflowY',
  'borderTopWidth','borderRightWidth','borderBottomWidth','borderLeftWidth','borderStyle',
  'paddingTop','paddingRight','paddingBottom','paddingLeft',
  'fontStyle','fontVariant','fontWeight','fontStretch','fontSize','fontSizeAdjust',
  'lineHeight','fontFamily',
  'textAlign','textTransform','textIndent',
  'textDecoration',  // might not make a difference, but better be safe
  'letterSpacing','wordSpacing',
  'tabSize','MozTabSize'
];
```

Plus `whiteSpace='pre-wrap'`, `wordWrap='break-word'` (textarea only),
`position:'absolute'`, and — critically — **`visibility:'hidden'`, not `display:none`**.
A `display:none` mirror has no layout and returns zeros.

The one browser sniff, with the Firefox bug numbered:

```js
if (isFirefox) {
  // Firefox lies about the overflow property for textareas: https://bugzilla.mozilla.org/show_bug.cgi?id=984275
  if (element.scrollHeight > parseInt(computed.height)) style.overflowY = 'scroll';
} else { style.overflow = 'hidden'; }
```

The wrapping-fidelity trick — the `<span>` holds the **entire remainder** of the text,
not a marker:

```js
// Wrapping must be replicated *exactly*, including when a long word gets
// onto the next line, with whitespace at the end of the line before (#7).
// The *only* reliable way to do that is to copy the *entire* rest of the
// textarea's content into the <span> created at the caret position.
span.textContent = element.value.substring(position) || '.';
```

**Two gaps that will bite.** `scrollTop`/`scrollLeft` appear **nowhere** in that file —
coordinates are content-relative and unadjusted for field scroll, which is the number
one integration bug. And `-webkit-text-security` is not copied and not in the list: the
mirror renders real glyphs while the field renders bullets, so every offset past char 0
is wrong. **Practical rule: refuse to measure password and text-security fields.**

**Harper's [`TextFieldRange.ts`](https://github.com/Automattic/harper/blob/master/packages/lint-framework/src/lint/TextFieldRange.ts)
is the better modern shape.** Its insight is to make the mirror a **full `Range`
provider** rather than a caret-point provider — since the mirror's content is a real
text node, you get native `getClientRects()` (multi-line splitting, bidi, graphemes) for
free.

```ts
private static arenas: WeakMap<HTMLTextAreaElement|HTMLInputElement,
  { mirror: HTMLDivElement; text: Text; refs: number }> = new WeakMap();
```

Four differences that matter: (a) **one persistent refcounted mirror per field** in a
WeakMap rather than create-and-destroy per call; (b) the mirror is positioned **exactly
over** the real field so rects come out already in viewport coordinates; (c) **scroll is
replicated and re-synced every measurement** (`mirror.scrollTop = field.scrollTop`);
(d) rects outside the field are filtered by `boxesOverlap`.

But Harper copies only **17** properties and drops `direction` (RTL fields mirror as
LTR), `wordSpacing`, `textIndent`, `textAlign`, `tabSize`, `fontVariant`, `fontStretch`,
`fontSizeAdjust`. And *neither* library copies `fontKerning`, `fontFeatureSettings`, or
`fontVariantLigatures`. Also note `getBoundingClientRect()` on `TextFieldRange` returns
the **mirror's** rect (the whole field), not the range's — so it is not a drop-in `Range`.

Grammarly's own mirror does the same thing with one scaling detail: the value is split
into **1000-char text nodes** (`_textNodeSize = 1000`) rather than one giant node.

### 2.5 Canvas `measureText` — mostly the wrong tool

A common belief worth correcting: **Monaco does not use canvas for character widths.**
[`charWidthReader.ts`](https://github.com/microsoft/vscode/blob/main/src/vs/editor/browser/config/charWidthReader.ts)
uses DOM measurement with an anti-subpixel trick — render the character **256 times** and
divide, recovering ~1/256 px from an integer `offsetWidth`:

```js
let testString = request.chr;
for (let i = 0; i < 8; i++) { testString += testString; }   // 2^8 = 256
testElement.textContent = testString;
...
request.fulfill(testElement.offsetWidth / 256);
```

Canvas `measureText` in VS Code appears only in `glyphRasterizer.ts` (the GPU glyph
atlas) and incidental UI sizing.

`measureText`'s limits: **no line wrapping** (no UAX#14), **no bidi**, **no shaping
across runs** — `measureText("f") + measureText("i") ≠ measureText("fi")` with an
fi-ligature, so per-character summing is systematically wrong for any kerned or
ligatured font. Plus subpixel accumulation error and silent font fallback if the webfont
hasn't loaded.

It does have one real use: `fontBoundingBoxAscent + fontBoundingBoxDescent` is the
closest canvas analogue to a range rect's height, since the spec defines that height as
font ascent + descent. Support: `actualBoundingBox*` Chrome 77 / FF 74 / Safari 11.1;
`fontBoundingBox*` Chrome 87 / FF 116 / Safari 11.1.

**Verdict: use it for font metrics, never for positioning.**

### 2.6 The modern alternative — CSS Custom Highlight API

[Spec](https://drafts.csswg.org/css-highlight-api-1/#introduction): highlights "that do
not affect the underlying DOM structure, but instead applies styles to text based on
range objects."

**Underlines are spec'd.** [css-pseudo-4 §3.5](https://drafts.csswg.org/css-pseudo-4/#highlight-styling)
allows `color`, `background-color`, **`text-decoration` and its associated properties
(including `text-underline-position` and `text-underline-offset`)**, `text-shadow`,
`stroke-color`/`fill-color`/`stroke-width`, and custom properties — with the warning
that "Historically (and at the time of writing) only `color` and `background-color` have
been interoperably supported."

Harper ships it in production anyway, with a fallback
([`Highlights.ts`](https://github.com/Automattic/harper/blob/master/packages/lint-framework/src/lint/Highlights.ts)):

```ts
const textDecor = `underline ${color} solid 2px`;
style.textContent = `::highlight(${tag}) { text-decoration: ${textDecor}; background-color: ${color}22; }`;
...
this.highlights = supportsCustomHighlights() ? new Map() : null;
```

Support per MDN browser-compat-data: `Highlight`/`CSS.highlights` — Chrome **105**,
Firefox **140**, Safari **17.2**. The `::highlight()` selector — Chrome 105, **Firefox
149**, Safari 17.2. **Feature-detect both**: Firefox 140–148 can register highlights
that never paint. Related: `::spelling-error`/`::grammar-error` — Chrome 121, Safari
17.4, not in Firefox; `text-decoration-line: spelling-error | grammar-error` (the native
platform squiggle) — Chrome 121 / FF 137 / Safari 26.2. MDN calls the API Baseline
"Newly available" since June 2025.

Two things to know. **Paint order puts custom highlights at the bottom** of the overlay
stack (`::selection` > `::target-text` > `::spelling-error` > `::grammar-error` >
`::highlight`). And the spec's performance clause:

> **Updating all `Range` objects as the DOM is modified has a significant performance
> cost. Authors who intend to observe DOM changes and react to them … are strongly
> encouraged to use `StaticRange`s in order to avoid this costly but unnecessary step.**

For a linter that rebuilds ranges on every change anyway, **`StaticRange` is correct** —
Harper's use of live `Range` leaves performance on the table. Also
`Highlight.type = "spelling-error" | "grammar-error"` gives assistive-tech semantics
without UA styling.

**This is the single biggest architectural shortcut available in 2026.** For
contenteditable it removes the entire rect-positioning problem: you hand the browser
ranges and it draws the underlines, correctly, through wrapping and bidi and scroll,
for free. It does **not** help inside textarea/input — the mirror is still required
there.

### 2.7 Performance

`Range.getClientRects()` and `getBoundingClientRect()` are named explicitly under
"Getting Range dimensions" in
[Paul Irish's forced-reflow gist](https://gist.github.com/paulirish/5d52fb081b3570c81e3a).
Three landmines specific to this problem:

1. **`elem.innerText` forces layout.** The pipeline "read innerText → lint → map offsets
   → getClientRects" forces layout *twice*, and the first is easy to miss.
2. **`getComputedStyle()` forces layout when the element is in a shadow tree** — and the
   mirror technique calls it on every construction, while extension overlays typically
   live in shadow roots.
3. **Setting `scrollTop` forces layout.** Harper's `syncMirror()` writes `scrollTop`
   *and* reads `getBoundingClientRect()` on every `getClientRects()` call: a
   read-write-read interleave per box.

The nuance most people miss, from the same gist: "Reflow only has a cost **if the
document has changed and invalidated the style or layout**." So N `getClientRects()`
calls with no intervening writes cost roughly one layout, not N. **The killer is
alternating.** Hence strict measure-then-mutate.

**Grammarly's own numbers are the best published figures anywhere:**

- "If you try to call `getBoundingClientRect` of a text field element **60 times per
  second** on a popular site like Facebook, it can easily consume **over 90% of CPU** on
  average hardware."
- [Reducing text input lag](https://www.grammarly.com/blog/engineering/reducing-text-input-lag/):
  overall input lag **−91%**; underline geometry chunking via `requestAnimationFrame`
  with a `Set` of unprocessed underlines gave **−50%** input latency; and **9% fewer
  users disabled the extension**. WebWorkers were rejected because "they do not allow
  access to the DOM." Field measurement used **Reservoir Sampling (Algorithm R)** at
  1–10% session sampling, capped at 10 events per session so power users don't skew the
  distribution.

**Observers.** `ResizeObserver` fires before paint but **not on position changes**.
`IntersectionObserver` gives `boundingClientRect` **asynchronously, off the
reflow-forcing path** — it is the cheap "did it move?" poll, and Grammarly uses it
exactly this way ("with some hacking we can get it to do what we need"). Use RO on the
editor root (it catches `resize: both` on a textarea, which fires no `window.resize`)
and IO for viewport movement and culling. Beware `content-visibility: auto` — a skipped
subtree has no layout, so measuring it forces the work you were skipping.

### 2.8 Keeping rects correct

Grammarly's own enumeration of what invalidates position, quoted in full because it is
the best checklist published anywhere:

> - Text field content change
> - Window scroll · Window resize
> - **Container scroll** — "same thing for **all scrollable ancestors**"
> - Text field scroll
> - Style and class attribute change
> - Other element attributes (e.g. `cols`, `rows`, `wrap` for `<textarea />`)
> - **All of the above, but for ancestors and all other elements on the page**
> - Addition and removal of elements elsewhere on the page
> - Global style sheet changes: insertion or removal of CSS rules and style sheets

with the concession: "For each of the above, **except global style sheet changes**,
there's an event you can subscribe to." Their last-resort fallback:

> **Polling: Regardless of any other signals, we're going to check up on the text field
> every second or so… it will provide a necessary fallback option to ensure that
> underlines will get aligned eventually.**

Per-hazard specifics:

- **Transforms.** `getClientRects()` **does** apply ancestor transforms (spec, quoted in
  §2.1) — in direct contrast to `offsetWidth`/`offsetTop`, which the same spec says
  **ignore** transforms. Never mix the two under a transform.
- **`position: fixed` overlays.** Any ancestor with `transform`, `filter`, `perspective`,
  `backdrop-filter`, `will-change` of those, or `contain: paint` creates a containing
  block for fixed — your "fixed" overlay silently becomes relative to it. Prefer
  attaching to `<body>` or the top layer.
- **Nested scrollers.** `scroll` doesn't bubble — use
  `document.addEventListener('scroll', h, {capture: true, passive: true})`.
  **mochi's current `window.addEventListener("scroll", paintMarks)` misses every inner
  scroller.**
- **Zoom.** There is no `zoomchange` event. Listen to `window.resize` **and**
  `window.visualViewport` resize, and watch
  ``matchMedia(`(resolution: ${devicePixelRatio}dppx)`)`` with a re-registering listener.
- **Shadow DOM.** A TreeWalker rooted in light DOM **will not descend into shadow
  roots** — walk each root separately. The Highlight spec ignores any range whose
  "shadow-including root is not that document."
- **Virtualised editors.** A live `Range` whose container was unmounted returns an empty
  rect list, and then `getBoundingClientRect()` gives `{0,0,0,0}`. Anchor offsets to
  document indices, not DOM order.
- **Fonts.** `await document.fonts.ready` before the first measurement — but the spec is
  emphatic that "a given `ready` promise is **only fulfilled once**, but further fonts
  may be loaded after it fulfills." Also subscribe to `document.fonts` `loadingdone`.

**Grammarly's key optimisation**, verbatim: position underlines **relative to the text
field**, not the viewport. Translate client coordinates from `getClientRects()` into
field-relative offsets and position the container on top of the field.

> "With this optimization, we will only need to recalculate underline coordinates either
> when the text content or text field size changes. **Scrolling and position changes
> will only require us to update the underline container element.**"

The caveat: you must query the field's `getBoundingClientRect()` in the **same batch** as
the `getClientRects()` calls, or you translate against a stale origin.

And the honest admission of what is still unsolved: the field "can be clipped if it's
overflowing in a container (which itself can also be overflowing, and so on,
recursively). It can also be covered by an element with `position: sticky`. … we can
solve it, though in many cases it will require us to put the underlines container
**closer to the text field element** in the DOM. And **that's a risk**."

## 3. Detection engine — client vs server, latency, protocol

### 3.1 The `capi.grammarly.com` protocol

Endpoint `wss://capi.grammarly.com/freews`, confirmed in three independent
reverse-engineerings
([bblanchon](https://github.com/bblanchon/reverse_engineering_grammarly_api),
[dexterleng](https://github.com/dexterleng/grammarly-api),
[znck/grammarly v0.13.2](https://github.com/znck/grammarly)). Auth is **cookies only**
on the upgrade — `gnar_containerId`, `grauth`, `csrf-token` — with anonymous sessions
minted by `GET https://auth.grammarly.com/v3/user/oranonymous?app=firefoxExt&containerId=...`.
The envelope is `{action, id, ...}` with a per-connection monotonic `id`; znck's client
is strictly serialised (one un-acked request in flight unless `priority: true`).

**It sends incremental OT deltas, never the full document after rev 0.** Two encodings
are in the wild. The legacy extension string form:

```json
{"ch": ["+0:0:\n:0"], "rev": 0, "action": "submit_ot", "id": 1}
{"ch": ["-0:1:\n:0+0:1:o:0"], "rev": 1, "action": "submit_ot", "id": 3}
```

and the Quill-style delta form used by the web editor:

```json
{"id":1,"action":"submit_ot","rev":0,"doc_len":0,
 "deltas":[{"ops":[{"insert":"I got grammarly working in code.\n\nAnd it's pointing at speling mistakes.\n"}]}]}
{"id":3,"action":"submit_ot","rev":1,"doc_len":74,"deltas":[{"ops":[{"retain":73},{"insert":"a"}]}]}
{"id":4,"action":"submit_ot","rev":2,"doc_len":75,"deltas":[{"ops":[{"retain":73},{"delete":1}]}]}
```

`rev` (pre-edit revision) and `doc_len` (pre-edit length) together are the **state
assertion** — a cheap way to detect desync without re-sending the document. `id` and
`rev` are independent counters. `submit_ot_chunk` exists for oversized initial documents.

**The `alert` response**, from a live capture of the text `Hello worlds!`:

```json
{"point":"NoCommaWithInterj",
 "transformJson":{"context":{"s":0,"e":13},"highlights":[{"s":0,"e":5}],
   "alternatives":[{"ops":[{"retain":5,"attributes":{"type":"important"}},
                           {"insert":",","attributes":{"type":"main"}}]}]},
 "title":"Missing punctuation after interjection",
 "sentence_no":0, "category":"BasicPunct", "group":"Punctuation",
 "pname":"Punctuation/BasicPunct/NoCommaWithInterj/InterjComma",
 "begin":5, "end":5, "rev":0,
 "highlightBegin":0, "highlightEnd":5, "highlightText":"Hello",
 "replacements":[","], "impact":"critical",
 "cardLayout":{"group":"Punctuation","rank":30,"outcome":"Correctness","outcomeRank":10},
 "action":"alert","id":3}
```

**The design lesson is in the offsets: `begin`/`end` (what to replace) is deliberately
separate from `highlightBegin`/`highlightEnd` (what to underline).** Here the replacement
is a zero-width insertion at offset 5, but the underline covers 0–5 ("Hello") so the user
sees context. `cardLayout.outcome` carries the Correctness/Clarity/Engagement/Delivery
bucket down the wire.

Offsets are **plain UTF-16 character offsets into the OT document**. Nothing DOM-shaped
appears anywhere in the message — one coordinate space, and third-party clients apply
them with raw `substring`, rebasing all five offset fields by the length delta.

`remove` events carry `hint: 'NOT_FIXED'` and `mergedIn` so the client knows *why* an
alert vanished (retracted vs absorbed) rather than resetting the whole set.

### 3.2 Sentence-level vs document-level

**Document-level state, sentence-level attribution, incremental re-check.** Three pieces
of evidence:

- znck, verbatim: "In response to `submit_ot` action, the server would send a series of
  `alert` actions, **which got affected by the change** triggered by `submit_ot`,
  followed by a `finished` action."
- `finished` carries **`checkedBegin`/`checkedEnd`** — the character range actually
  re-analysed for that revision.
- Every alert carries **`sentence_no`** (0-based sentence index).

The [2025 suggestions post](https://www.grammarly.com/blog/engineering/how-suggestions-work-grammarly-editor/)
notes a suggestion can now "restructure a paragraph… or even make changes across the
whole document", so document-scope analyses coexist with sentence-scoped ones.

### 3.3 Debounce — no published constant, but a documented mechanism

**There is no "N ms after typing stops" figure in any primary source.** What *is*
documented:

- The mechanism, from [reducing text input lag](https://www.grammarly.com/blog/engineering/reducing-text-input-lag/):
  the extension "**buffers text revisions and visually updates the highlights by one
  character when the user is typing. Once the user stops typing, the extension processes
  any pending text revisions.**"

  This is a **deferral of analysis, not a suppression of underlines** — existing
  highlights shift by one character per keystroke so they track visually. Do not copy a
  naive "hide while typing"; it flickers.
- The design assumption, in one sentence: "**users don't interact with suggestions until
  they're done typing** (except in cases like autocorrect)."
- Batching rationale, from
  [Part 1: hidden complexity in front-end applications](https://www.grammarly.com/blog/engineering/part-1-how-grammarly-tackles-hidden-complexity-in-front-end-applications/):
  "An average writer types 120 characters per minute, and to optimize performance, it is
  better to group batches together."
- The end-to-end budget: "Grammarly must provide high-quality suggestions in real
  time—**less than 100 milliseconds**"
  ([on-device models at scale](https://www.grammarly.com/blog/engineering/on-device-models-scale/)).

A "48 ms LSP baseline" figure circulating in search results comes from a content farm.
Do not rely on it.

### 3.4 Client vs server — this has flipped recently

**Historically: everything server-side.** 2019-era captures show a single-character
document round-tripping to CAPI for a verdict. The personal dictionary is a server-side
account setting.

**Now: a quantised on-device language model.** Two 2025 posts:

[On-Device AI at Scale](https://www.grammarly.com/blog/engineering/on-device-models-scale/)
(Sri Malireddi): "we built a **Rust-based SDK** that runs Grammarly machine learning
models across three key platforms: Mac, Windows, and **Chrome Extension**." A T5 GEC
model went **~4 GB → <300 MB**, and **70 → 297 tokens/sec**, using BFLOAT16 over INT4,
MLX-optimised MHA, and Metal on Apple silicon. "To ensure a real-time user experience,
we calculated that the entire GEC model must run at 100+ tokens/second, which required
us to reduce latency by 50%."

[One Model to Rule Them All](https://www.grammarly.com/blog/engineering/efficient-on-device-writing-assistance/)
(Dhruv Matani, Apr 2025): a single **~1B-parameter Llama-based decoder** doing joint
spelling and grammar correction, with Grouped Query Attention, 16-bit → 4-bit
quantisation (−70% memory), **~210 tok/s on an M2 Mac**, "runs entirely in device memory
without server dependency", trained partly on synthetic errors generated by a T5 model.

**Neither post mentions WebAssembly or ONNX.** The Chrome Extension is listed as a
Rust-SDK target, which strongly implies a WASM build, but it is never stated.

The trajectory is unambiguous and it is the strategically important finding here:
**Grammarly is moving detection to the client.** A design that assumes a server round
trip is designing toward where they were, not where they are going.

**Two gotchas.** `span` is a **method call on `Lint`, not a property** — the
[spans doc](https://github.com/automattic/harper/blob/master/packages/web/src/routes/docs/harperjs/spans/+page.md)

are **character (Unicode scalar) indices, not byte offsets** — the doc calls this out as
a common misconception.

`LocalLinter` vs `WorkerLinter`, from the
[linting doc](https://github.com/automattic/harper/blob/master/packages/web/src/routes/docs/harperjs/linting/+page.md):

> A `LocalLinter` will instantiate and prepare Harper's WebAssembly module asynchronously,
> but **in the same event loop**. This can result in high LCP... **In other words:
> `LocalLinter`s are not for the web.**

**Can harper.js run in a Chrome MV3 content script? Yes — and Harper ships it themselves.**

They maintain their own MV3 extension at
[`packages/chrome-plugin`](https://github.com/automattic/harper/tree/master/packages/chrome-plugin).
The definitive answer is in
[`src/manifest.ts`](https://github.com/automattic/harper/blob/master/packages/chrome-plugin/src/manifest.ts):

**The key architectural decision: the WASM does not run in the content script. It runs in
the background service worker.** The content script holds zero WASM and calls out over a
message protocol:

```typescript
const fw = new LintFramework(
	(text, domain, options) => ProtocolClient.lint(text, domain, options),
	{ ignoreLint: (hash) => ProtocolClient.ignoreHash(hash), ... }
);
```

This matters because the `extension_pages` CSP — where `wasm-unsafe-eval` applies —
covers the service worker and extension pages, **not** the host page, whose CSP a
page-world script would be subject to. Running WASM in the SW sidesteps the entire class
of host-CSP problems. There is also a 400 ms keep-alive ping to stop Chrome killing the
worker:

```typescript
const keepAliveCallback = () => {
	ProtocolClient.lint('', 'example.com', {});
	void syncGoogleDocsBridge();
	setTimeout(keepAliveCallback, 400);
};
```

Four WASM binary import forms exist in `harper.js`'s `exports`: `harper.js/binary`,
`harper.js/slimBinary`, `harper.js/binaryInlined`, `harper.js/slimBinaryInlined`. The
`*Inlined` forms avoid a separate `.wasm` fetch; the extension instead ships the raw
`.wasm` as a `web_accessible_resource`.

**Directly relevant to mochi:** the extension already has
[`src/isSubstack.ts`](https://github.com/automattic/harper/blob/master/packages/chrome-plugin/src/isSubstack.ts)
and auto-enables on Substack:

```typescript
if (isWordPress() || isSubstack()) {
	ProtocolClient.setDomainEnabled(window.location.hostname, true, false);
}
```

`isSubstack()` checks hostname `substack.com`/`*.substack.com`, then falls back to
`link[rel="preconnect"][href*="substackcdn.com"]`,
`meta[property="og:title"][content*="| Substack"]`, and
`meta[name="description"][content*="a Substack publication"]` — a ready-made detector
for custom-domain Substacks.

**Custom rules: not Rust-only.** This is the biggest finding in this section and it
contradicts the common assumption. Harper has a declarative rule language called
[**Weir**](https://github.com/automattic/harper/blob/master/packages/web/src/routes/docs/weir/+page.md),
packaged into **Weirpacks** — zip archives loadable **at runtime from JavaScript**.

A complete rule:

```plaintext
expr main [(G [Suite, Suit]), (Google Apps for Work)]

let message "Use the updated brand."
let description "`G Suite` or `Google Apps for Work` is now called `Google Workspace`"
let kind "Miscellaneous"
let becomes "Google Workspace"
let strategy "Exact"

test "..." "..."
allows "..."
```

The expression grammar covers words (case-insensitive), sequences `()`, alternatives
`[]`, filters `<>` (narrow a match to a sub-span), UPOS tags written literally
(`expr main DET NOUN`), `PROG` for progressive verbs, exceptions with `!`
(`expr main DET !NOUN`), token-level wildcards `*`, self-matching punctuation, and
expression references `@vehicles`. `let strategy` is `Exact` or `MatchCase`; `let scope`
is `Chunk` (default) or `Sentence`. Inline `test "A" "B"` and `allows "A"` assertions run
via `harper-cli test <file>`.

Weirpacks are ZIPs with one `.weir` file per rule plus a `manifest.json`. Loaded from JS:

```typescript
loadWeirpackFromBlob(blob: Blob): Promise<WeirpackTestFailures | undefined>;
export type WeirpackTestFailures = Record<string, WeirpackTestFailure[]>;
```

Note it **returns the test failures rather than silently accepting a broken rule**.
`harper.js` also exports `packWeirpackFiles(files: Map<string,string>): Uint8Array` and
`unpackWeirpackBytes`, so you can author and pack a Weirpack entirely in the browser.
There is a live [Weir studio](https://writewithharper.com/weir/studio), and the
extension's background worker has `AddWeirpackRequest`/`RemoveWeirpackRequest` in its
protocol. Background reading:
[Building the Weir Language](https://elijahpotter.dev/articles/building-the-weir-language).

**The limit:** Weir is pattern- and phrase-shaped. Anything needing real logic
(statistical, cross-sentence, dictionary-driven, or counting — e.g. "70% of paragraphs
are one sentence") still requires a Rust linter in `harper-core`. That boundary is
directly load-bearing for mochi and is picked up in §7.

[`harper-core/src/linting`](https://github.com/automattic/harper/tree/master/harper-core/src/linting)
has roughly 325 entries, so about 300+ built-in linters, rendered at
<https://writewithharper.com/docs/rules>. The docs warn: "it is not recommended for
consumers of `harper.js` to rely on any rule to exist" — they add rules daily, so a
settings UI must tolerate unknown keys.

**Performance.** [`COMPARISON.md`](https://github.com/automattic/harper/blob/master/COMPARISON.md)
gives "Suggestion Time": **Harper 10 ms**, LanguageTool 650 ms, Grammarly 4000 ms. The
README claims "milliseconds to lint a document" and "less than 1/50th of LanguageTool's
memory footprint", and states "We consider long lint times bugs." These are Harper's own
unaudited figures.

**And the overlay engine is separately reusable.**
[`packages/lint-framework/src/lint/`](https://github.com/automattic/harper/tree/master/packages/lint-framework/src/lint)
is a self-contained Apache-2.0 solution to §2: `Highlights.ts`, `Box.ts`, `RenderBox.ts`,
`TextFieldRange.ts`, `computeLintBoxes/`, `SourceElement.ts`, `spanMapping.ts`,
`SuggestionBox.ts`, `PopupHandler.ts`, `lintKindColor.ts`, `googleDocsAdapter.ts`,
`domUtils.ts`. This is arguably as valuable as the linter itself — it is the hard part,
already solved, already proven on Substack.

### 4.2 write-better — do not use

- **License: none.** The GitHub API returns `"license": null` and there is **no LICENSE
  file** in the repo. The README doesn't state one. Legally this is all-rights-reserved:
  it cannot be used or forked. That alone disqualifies it.
- **Unmaintained** — last push 2023-02-03, 65 stars.
- Engine: a personal fork of [write-good](https://github.com/btford/write-good)
  (`"write-good": "github:justiceo/write-good"`).
- **Highlighting is DOM injection, not overlay** —
  [`src/content-script/highlight.ts`](https://github.com/justiceo/write-better/blob/master/src/content-script/highlight.ts)
  wraps offending text in a real `<span>` inserted into the page:

  ```typescript
  const el = document.createElement('span');
  el.innerText = textSegment.substring(suggestion.index, suggestion.index + suggestion.offset);
  el.classList.add('writebetter-highlight', suggestion.type);
  ```

  This is precisely the approach Grammarly abandoned, and it only ever worked against
  Google Docs' legacy HTML-rendered DOM. Docs moved to canvas rendering from 2021, which
  breaks it entirely — tellingly the repo contains a `canvas-highlighting-demo.html`
  next to `highlight.ts`, suggesting they hit that wall and stopped.

The correction to mochi's existing `docs/research.md`, which lists write-better as
"open source" and worth reading: **it has no license and its highlighting approach is the
anti-pattern.** It should be dropped from the reference list.

### 4.3 codextde/textchecker — alive, but a different product

- **License: MIT.** Not archived, last push 2026-02-02, 43 stars, TypeScript.
- **It is not a rule engine — it is an LLM proxy.** The
  [README](https://github.com/codextde/textchecker): "Provides grammar, spelling, and
  style checking using AI models, powered by your own API keys" — Gemini, OpenAI, or
  Claude, keys in Chrome sync storage.
- Origin: built in reaction to LanguageTool making its extension
  [Premium-only in January 2025](https://languagetool.org/de/webextension/premium-announcement).
- Built with WXT, ships Chrome + Firefox. Real-time or hotkey (Cmd+Shift+G) checking,
  inline underlines with click-to-fix popovers, personal dictionary.

Useful as a reference for a *judgement tier*, and MIT-licensed so it is forkable — but it
gives nothing deterministic, and every keystroke-triggered check costs an API call.

### 4.4 LanguageTool — good API, bad extension reference

**The currently-shipped LT extension is closed source.** The only extension repo in the
org, [`languagetool-org/languagetool-browser-addon`](https://github.com/languagetool-org/languagetool-browser-addon),
is LGPL-2.1, **Manifest V2**, last pushed 2023-03-01, and its own README says "This is
our old add-on. We recommend using the new one instead."

**And it is not a reference implementation for underlines at all.** Grepping the whole
extension for `getClientRects|underline|mirror|createRange` returns zero hits. It renders
a **corner badge with an error count** pinned to the focused field
(`webextension/cs/textarea.js`); clicking it opens a modal iframe where matches are
re-rendered as plain text with a repeating squiggle PNG background
(`.error { background-image: url("../images/squiggle.png") }`). Google Docs was handled
by an entirely separate, unreleased extension. Gmail support is per-site fudge factors
(`getElementById(":4")`, `gmailComposeToolbarHeight = 155`,
`DOMAIN_SETTINGS = { "twitter.com": {left: -22} }`). Debounce is
`BG_CHECK_TIMEOUT_MILLIS = 1500`.

Two genuinely reusable ideas survive: `share/markup.js`'s `html2markupList()` (HTML →
offset-preserving `[{text},{markup}]` list, mapping block tags to `\n\n`), and the
synthetic-event trick for making framework editors accept programmatic mutations —
`simulateSelection()` dispatching fake `mousedown`/`mouseup`, then `InputEvent("input")`
plus `Event("change")`.

**The HTTP API is the useful part.**
[Swagger](https://languagetool.org/http-api/languagetool-swagger.json), `POST /v2/check`,
form-encoded. Required: `language` (`en-US` or `auto`), plus one of `text` or `data`.
Optional: `enabledRules`, `disabledRules`, `enabledCategories`, `disabledCategories`,
`enabledOnly`, `level` (`picky`), `motherTongue`, `preferredVariants`.

Verified live response shape:

```json
{ "matches": [ {
  "message": "The singular demonstrative pronoun ‘this’ does not agree with the plural verb ‘are’...",
  "shortMessage": "Grammatical problem: use ‘these’",
  "replacements": [ { "value": "These" } ],
  "offset": 0, "length": 4,
  "context": { "text": "This are a test of the LanguageTool api...", "offset": 0, "length": 4 },
  "sentence": "This are a test of the LanguageTool api.",
  "rule": { "id": "THIS_NNS", "subId": "5", "sourceFile": "grammar.xml",
            "issueType": "grammar", "category": { "id": "GRAMMAR", "name": "Grammar" },
            "isPremium": false, "confidence": 0.64 } } ] }
```

Three traps: (a) `matches[].offset/length` are 0-based character offsets into your
submitted text — use these; `context.offset/length` index the *truncated* `context.text`,
a different coordinate space. (b) `replacements` can be enormous — a single typo returned
**1,928** entries; slice before rendering. (c) Free rate limits are 20 req/min and 20,000
chars/request.

The `data` annotation parameter
(`{"annotation":[{"text":".."},{"markup":"<b>"},{"markup":"<p>","interpretAs":"\n\n"}]}`)
keeps markup out of the offsets by design — better than hand-flattening editor DOM. This
is a pattern worth copying regardless of whether LT itself is used.

**Core:** LGPL-2.1-or-later, ~14.8k stars, actively maintained. Rules are XML pattern
rules in `grammar.xml` — **8.2 MB, 142,511 lines** for English:

```xml
<rule id="TROJAN_HORSE_CASING" name="trojan (Trojan) horse">
    <pattern>
        <marker><token case_sensitive="yes">trojan</token></marker>
        <token regexp="yes">horses?|virus(es)?|asteroids?|points?</token>
    </pattern>
    <message><suggestion>Trojan</suggestion> refers to a proper noun and needs to be capitalized.</message>
</rule>
```

Token attributes include `regexp`, `postag`+`postag_regexp`, `chunk`/`chunk_re`,
`case_sensitive`, `min`, `skip`, `scope`, plus `<antipattern>` and `<exception>`. About
60 Java rule classes handle what XML can't. **n-gram data is a separate ~8 GB download**,
and neural rules are remote-only.

## 5. Rule engines — how rules are expressed

| | write-good | retext | textlint | Harper (Weir) | Harper (Rust) | LanguageTool | mochi today |
|---|---|---|---|---|---|---|---|
| License | MIT | MIT | MIT | Apache-2.0 | Apache-2.0 | LGPL-2.1 | — |
| Model | Regex on raw string | AST visitor (nlcst CST) | AST visitor (TxtAST) | Declarative pattern DSL | Rust trait impl | XML pattern rules | Lua string patterns |
| POS-aware | No | Partially (plugins) | Via plugins | **Yes** (UPOS tags) | Yes | Yes (`postag`) | No |
| Runtime-addable rules | **Yes** (`{checks:{fn}}`) | No (bundled plugins) | No (compile-time) | **Yes** (Weirpack from JS) | No | Yes (XML) | Yes (edit + reload) |
| Auto-fix | No | No | **Yes**, first-class | Yes (`becomes`) | Yes | Yes | No |
| Self-testing rules | No | No | Yes | **Yes** (`test`/`allows` inline) | Yes | Yes | Yes (`rules_spec.lua`) |
| Cross-block / counting rules | No | Hard | Hard | **No** | Yes | No | **Yes** |
| Browser | Bundleable (CJS) | Yes | Yes (Worker compile) | Yes (WASM) | n/a | Server only | n/a |
| Maintained | 2025-03 | 2025-02 (dormant) | 2026-08 | active | active | active | — |

### write-good

Pure regex, no parsing at all. Sentence splitting is literally
`'([^\n\.;!?]+)([\.;!?]+)'` with a source comment saying "this implementation is really
naive." Checks return `{index, offset}` where `offset` is the match **length**, not an
end index; the driver adds `reason`. Nine built-ins: `passive`, `illusion`, `so`,
`thereIs`, `weasel`, `adverb`, `tooWordy`, `cliches`, `eprime`.

**Custom checks are genuinely runtime** — pass `{checks: {name: {fn, explanation}}}`, no
build step. Caveat: `opts.checks` **replaces** the defaults rather than merging, and
`defaultChecks` is not exported.

This is essentially the same expressive power mochi's Lua rules already have.

### retext

unified/nlcst plugin = an attacher returning `(tree, file) => void`. A real plugin,
[retext-repeated-words](https://github.com/retextjs/retext-repeated-words):

```js
visit(tree, 'SentenceNode', function (parent) {
  const start = pointStart(parent.children[previous.index]);
  const end = pointEnd(child);
  const message = file.message('Unexpected repeated `' + value + '`, remove one occurrence',
    { ancestors: [parent, child], place: {start, end},
      ruleId: current.value.replace(/\W+/g, '-'), source: 'retext-repeated-words' });
  message.actual = ...; message.expected = [value];
});
```

Note the current vfile signature is `VFile#message(reason[, options])` with
`{place, source, ruleId, ancestors}` — the older `file.message(reason, node, origin)` form
is obsolete. Bundle sizes min+gzip: `retext` 15.6 kB, `retext-passive` 3 kB,
`retext-simplify` 6.1 kB, `retext-readability` 19.8 kB, `retext-equality` 20.3 kB.
`retext-usage` is **deprecated**; `retext-overuse` is stale (2017, pre-ESM). Core repo
dormant ~18 months.

retext has the **richest message model** — `{place, source, ruleId, actual, expected, url}`
is worth copying as a finding schema regardless of engine.

### textlint

ESLint-shaped, and the nicest rule-authoring ergonomics of the three:

```js
export default function (context) {
    const { Syntax, report, RuleError, getSource, locator } = context;
    return { [Syntax.Str](node) {
        const match = getSource(node).match(/typo/);
        if (match) report(node, new RuleError("Found a typo", {
            padding: locator.range([match.index, match.index + match[0].length]) }));
    } };
}
```

Fixable rules export `{linter: reporter, fixer: reporter}` and use
`context.fixer.replaceTextRange([start,end], text)`. `RuleError` also supports
`suggestions[]`. Browser support via `@textlint/kernel` or `@textlint/script-compiler`
(compiles `.textlintrc` plus rules into a single Web Worker bundle) — but the **rule set
is fixed at compile time**; only rule *options* change at runtime. Roughly 300 published
`textlint-rule-*` packages. Real markup handling via pluggable parsers, so it skips code
blocks natively.

### Which is most extensible for custom style rules?

For rules of the shape "no adverbs", "active voice only", "never say *leverage*":

**Harper's Weir wins**, for three reasons the others cannot match:

1. **It is POS-aware without you doing any NLP.** `expr main !PROG` or `expr main DET NOUN`
   gets part-of-speech matching from `harper-brill` for free. mochi's current adverb rule
   is `-ly` minus a deny-list, and its passive rule is "a form of *to be* followed by
   something ending in -ed" — both are exactly the heuristics Weir replaces with real
   tagging. `Lexicon.notAdverbs` exists purely because there is no POS tagger; it goes away.
2. **Rules are runtime-loadable from JavaScript** via `loadWeirpackFromBlob()`, and
   packable in-browser via `packWeirpackFiles()`. textlint compiles rules in; retext
   bundles plugins. Weir does neither.
3. **Rules carry their own tests inline** (`test`/`allows`), and loading returns the
   failures rather than accepting a broken rule. mochi already has `rules_spec.lua`, so
   this is a philosophy match, not a new discipline.

**The honest limit, and it matters for mochi:** Weir is per-match, pattern-shaped, and
scoped to `Chunk` or `Sentence`. It cannot express *any* of mochi's structural rules:

- `Rules.length` — total word count against an 800–2000 band
- `Rules.rhythm` — "paragraph runs 5+ sentences", "70% of paragraphs are one sentence"
- `Rules.tenPercent` — this draft vs the previous snapshot
- `Rules.title` — a rule about a *field*, not the body

These are counting and comparison over the whole document plus history. **No pattern DSL
does them, and no off-the-shelf engine does them.** They are also, not coincidentally,
the rules that carry `severity = "structural"` — the ones mochi actually interrupts for.

That split is the central finding of this document and it drives §7.

## 6. UX patterns

### 6.1 Colours

From [Grammarly's product blog](https://www.grammarly.com/blog/product/better-writing-with-grammarly/),
verbatim: **red** = "spelling, punctuation, and grammar" (Correctness); **blue** =
"potential clarity and conciseness improvements" (Clarity); **green** = "suggestions to
make your writing more engaging" (Engagement); **purple** = "help you strike the right
balance of politeness, formality, and friendliness" (Delivery). Launched July 2019.

Watch out: Engadget and TechSpot both have the last two **swapped**. Grammarly's own docs
are authoritative.

There is a **fifth colour**: gray for style-guide violations, per the
[Editor user guide](https://support.grammarly.com/hc/en-us/articles/360003474732-Grammarly-Editor-user-guide).
And two of the four are a **paywall signal, not purely semantic** — Engagement and
Delivery are Premium-only. The taxonomy is partly a pricing artefact, which is a reason
not to copy it wholesale.

The August 2025 redesign rebuilt the surface on the acquired Coda platform; the new agent
"presents recommendations in dynamic categories that are tailored to your writing
context" — a shift away from a fixed taxonomy.

### 6.2 Passive underline vs suggestion card

**Hover discloses, click commits.** From
[support](https://support.grammarly.com/hc/en-us/articles/5321259769357-I-don-t-see-the-full-list-of-suggestions-when-using-the-Grammarly-browser-extension):
"To accept a suggestion, **hover over the underlined text and click the card that
appears**."

The floating button sits in the **lower-right corner of the text field** and shows the
suggestion **count**: "the icon in the lower-right corner of the text field will show the
number of suggestions." A second green lightbulb button is the generative-AI entry.

**A key asymmetry worth designing around:** in the browser extension, non-org users
**cannot see all suggestions at once** — "suggestions are displayed one at a time after
clicking the extension's widget." The full sidebar list is a paid affordance. The
extension deliberately trades completeness for non-intrusiveness. So the underline layer
carries *everything*; the card carries *one thing*; the count carries *the aggregate*.

Card actions: **Accept**, **Dismiss**, **Learn more**, **More Actions** → "flag the
suggestion as incorrect or offensive" (the "not for me" path), and **Add to dictionary**.

### 6.3 Not being annoying while typing

The mechanism is **deferral of analysis, not suppression of underlines** (§3.3). Existing
highlights shift by one character per keystroke so they track visually; pending revisions
are processed once typing stops. Copying a naive "hide while typing" produces flicker,
which is worse.

The invalidation architecture, from
[How Suggestions Work](https://www.grammarly.com/blog/engineering/how-suggestions-work-grammarly-editor/):
three components — **Suggestion Repository** (registered/applied), **Delta Manager**
("rebases suggestion Deltas according to new changes coming in" so offsets stay correct
without waiting for the server round-trip), **Highlights Manager**. Granularity:
"suggestions that span more text only need to be hidden if a user makes changes to the
phrases highlighted in the suggestion card."

The stated UI invariants are narrow and mechanical, and worth adopting verbatim:
**cards must not flicker**, and **suggestions must always apply instantly**.

**Caret-proximity suppression is not confirmed.** I found no evidence Grammarly withholds
suggestions specifically in the sentence containing the caret. The two documented
behaviours are debounce-until-typing-stops and invalidate-on-edit-of-the-highlighted-span.
(mochi already reads `caret` in its snapshot for exactly this purpose — that is a mochi
design decision, not a copy of Grammarly.)

### 6.4 Acceptance data

**Grammarly has never published a suggestion acceptance rate.** The tell is their own
[Analytics API](https://developer.grammarly.com/analytics-api.html), which exposes only
`days_active`, `sessions_count`, `sessions_improved_percent`, `prompt_count` — **no
suggestions-shown or suggestions-accepted metric at all**. They measure at session level,
not suggestion level.

The best quantitative evidence on suggestion *timing* comes from the code-assistant
literature — [arXiv 2511.18842](https://arxiv.org/html/2511.18842), a two-month
deployment with professional developers:

| Timing | Acceptance |
|---|---|
| No delay | **4.9%** |
| Static delay | **15.4%** |
| Adaptive timing | **18.6%** |

Blind rejections (rejected without being read) fell **8.3% → 0.36%**, with 75% fewer
wasted inference calls. That is roughly **3.8× acceptance from delay alone** — the
strongest published argument that *when* you show a suggestion matters more than how good
it is.

Writing-specific: [AnchoredAI](https://arxiv.org/pdf/2509.16128) (2025) found
position-anchored AI comments increase writer agency, ownership, and acceptance versus
detached ones — empirical support for inline underlines over a pure sidebar.
[Reactive Writers, CHI 2026](https://dl.acm.org/doi/10.1145/3772318.3791529) found rapid
inline suggestions **interrupt ideation**, redirecting attention to agreement-based
evaluation. A [CHI 2025 co-writing study](https://dl.acm.org/doi/10.1145/3706598.3713205)
names Grammarly specifically: excessive suggestions "can interrupt the writing flow."

**Negative finding: NN/g has no article on inline writing-assistant suggestion UX** — no
piece on underline colour semantics, hover-card timing, or interruption cost. The closest
transferable principle, from
[Designing Use-Case Prompt Suggestions](https://www.nngroup.com/articles/designing-use-case-prompt-suggestions/):
short suggestions can be shown several at once; complex ones need real estate and should
be presented **one at a time**.

**This validates mochi's existing design.** `nag.lua`'s `PAUSE_SECONDS = 20`,
`LIVE_COOLDOWN = 6`, `MAX_LINES = 4`, and the never-say-the-same-thing-twice signature
check are all in the direction the research points. mochi's three modes (live / pause /
ask) are a more honest version of "adaptive timing" than anything Grammarly ships.

## 7. Legal note on the technique

Worth recording because it de-risks the whole plan. I queried Google Patents for
assignee "Grammarly" (34 results; note assignee has shifted to **Superhuman Platform Inc.**
on several records as of Nov 2025, so any freedom-to-operate search must query both).

**Exactly one patent covers overlay mechanics:
[US11880644B1](https://patents.google.com/patent/US11880644B1/en)**, "Inferred event
detection and text processing using transparent windows," filed 2021-11-12, granted
2024-01-23. **It is desktop-scoped**, keyed to OS accessibility APIs. Claim 1 covers
subscribing to accessibility-API events → "receiving a **layout change event**" →
determining a focus change → "**generating a transparent window on top of the currently
focused element**" → receiving "**character ranges**" → determining "**screen bounds**"
→ displaying markup there. The most informative dependent limitation is "querying an
accessibility API separately for each of the one or more character ranges" — the desktop
analogue of per-range `getClientRects()`.

[US9002700B2](https://patents.google.com/patent/US9002700B2/en) (filed 2011) mentions
cards in the **specification only, not the claims**: "Feedback cards may overlay text in
the editor, such as with an arrow pointing at the sentence and/or word that triggered the
feedback card." Disclosed but unclaimed — published prior art, not an enforceable monopoly.

**Explicit negative findings:**

1. **No patent covers the browser-extension overlay technique.** The full method —
   `Range.getClientRects()`, coordinate translation, scroll/resize/mutation/IO plus ~1 Hz
   polling — was **published on the engineering blog and not patented**. A
   disclosure-not-patent posture.
2. No patent claims underline colour-coding by category.
3. No patent claims hover-to-reveal or click-to-reveal card interaction.
4. No patent claims suppression or debouncing of suggestions while typing.

The web technique is legally clear. Note that item 1 does **not** extend to the desktop
accessibility-API approach, which US11880644B1 does claim — relevant if mochi ever
considers reading native macOS apps through the AX API.

## Recommendation for mochi

### What mochi has

- **(a)** A Chrome MV3 content script reading Substack's ProseMirror DOM into a
  `{title, subtitle, blocks[], body, words, caret}` snapshot, debounced at 400 ms, with a
  paragraph-level overlay layer (`ensureLayer`/`paintMarks`) that draws a 2px rule under
  a whole block via `getBoundingClientRect()`.
- **(b)** A pure-Lua deterministic rules engine in Hammerspoon — eight rules, two
  severities, no `hs.*` dependency, tested outside Hammerspoon via `rules_spec.lua`.
- **(c)** A localhost WebSocket bridge (`ws://127.0.0.1:27852/mochi`) where writing mode
  **stops the server** rather than ignoring messages, so "mochi is not reading" is
  verifiable from outside the process.

Three things are already right and should not be touched: the **overlay-not-injection**
decision, the **closed-port privacy claim**, and **`nag.lua`'s timing discipline**. The
research validates all three — the first by Grammarly's own post-mortem, the second by
being a stronger claim than anything Grammarly can make, the third by the 3.8×
delay-versus-acceptance data.

### The recommendation

**Split the rules engine along the boundary the research exposes, and put the split where
the data already lives. Do not move mochi's rules into the browser, and do not put
Harper's job into Hammerspoon.**

Concretely: **Harper (WASM, in the extension's service worker) becomes the span tier.
Hammerspoon keeps the document tier. Both already exist; neither needs porting.**

The reason is §5's finding, which is sharper than a latency argument. mochi's eight rules
divide cleanly in two:

| Tier | Rules | Shape | Where it belongs |
|---|---|---|---|
| **Span** | `adverbs`, `passive`, `inflated`, `stadium` | "this word, here" — per-match, pattern-shaped, wants POS tagging | **Browser.** Harper built-ins + a mochi Weirpack |
| **Document** | `length`, `rhythm`, `tenPercent`, `title` | counting, ratios, comparison against the previous draft, a rule about a *field* | **Hammerspoon.** Nothing off-the-shelf does these |

Note what falls out of that table: **every `severity = "structural"` rule is in the
document tier, and every `nag` rule except `stadium` is in the span tier.** The split is
not arbitrary — it already matches mochi's own interruption model. The span tier is what
you underline; the document tier is what the pet speaks. That is the same distinction
Grammarly draws between its underline layer and its card, arrived at independently.

### Why the rules engine should not move into the browser

1. **The document tier has no home there.** Weir cannot count sentences per paragraph,
   cannot compute a one-sentence-paragraph ratio, and structurally cannot compare this
   draft to the previous one — that requires state across snapshots, which is what
   Hammerspoon already holds. Porting it to JS would mean rewriting working, tested Lua
   into an environment that is *harder* to test, for no gain.
2. **Latency is already a non-issue for the document tier.** These rules fire on
   word-count and paragraph-shape changes, and they surface through `nag.lua` at 6–20
   second cadences. A localhost WebSocket round-trip is sub-millisecond. Optimising it
   would be optimising the wrong number.
3. **The privacy claim depends on it.** `bridge.lua` stops the server rather than
   ignoring messages, and that is the strongest statement mochi makes. Moving judgement
   into the browser weakens it — a closed port is a fact; a disabled code path is a claim.
4. **The pet lives in Hammerspoon.** Whatever decides when mochi speaks must sit next to
   the pet, and `nag.lua` is where that logic already is.

### Why the span tier should move into the browser

1. **Latency actually matters there.** An underline must track the text, and §2.7's
   measure-then-mutate discipline requires the lint result and the rect computation to be
   in the same frame budget. A round trip to Hammerspoon per keystroke would make the
   `requestAnimationFrame` chunking that gave Grammarly its −50% input latency impossible
   to implement.
2. **Harper is strictly better at these four rules than mochi's Lua is, today.** mochi's
   adverb rule is `-ly` minus `Lexicon.notAdverbs`; its passive rule is "a form of *to be*
   followed by something ending in `-ed`" plus an irregular-participle table. Both exist
   only because there is no POS tagger. Harper has `harper-brill`, and Weir lets you write
   `expr main !PROG` instead of maintaining deny-lists. `Lexicon.notAdverbs` and
   `Lexicon.irregularParticiples` go away.
3. **It is offline and free.** Apache-2.0, WASM, no network, no key, no account. This
   preserves the property that mochi works on a plane, which the LLM-proxy alternatives
   (textchecker, GemType) do not.
4. **The mochi-specific rules survive as data.** `Lexicon.stadium` and `Lexicon.inflated`
   are phrase → replacement tables — precisely Weir's `let becomes` shape, with inline
   `test`/`allows` assertions replacing the current spec file. They stay mochi's voice;
   only the matcher changes.

### Minimum-change path

Four phases, each shippable and independently reversible. Phases 1 and 2 are unordered.

**Phase 1 — generalise the surface. No engine change.**

The single highest-leverage change, and it touches only `content.js`:

- Replace `findEditor()`'s Substack-specific cascade with **capture-phase `focus` on the
  document** plus `composedPath()[0]` and recursive `shadowRoot.activeElement` descent
  (§1.1). Adopt Grammarly's eligibility gates — min 250×35 px, skip `dir="rtl"`, skip
  `readonly`/`disabled`, skip `type=password` and `-webkit-text-security` (§2.4).
- Keep the ProseMirror path as a *specialisation*, not the entry point. Steal
  `isSubstack.ts`'s custom-domain detector (§4.1) so mochi's playbook still activates on
  a Substack served from `yourname.com`.
- Fix the two positioning bugs already present: `window.addEventListener("scroll")`
  misses inner scrollers — use `document.addEventListener('scroll', h, {capture:true, passive:true})`
  (§2.8); and add a ~1 Hz polling fallback, because as Grammarly documents, global
  stylesheet changes have no event.
- Extend the `draft` contract with a `surface` field (`prosemirror` / `contenteditable` /
  `textarea`). `bridge.lua`'s `decode()` already validates field-by-field, so this is
  additive and the document rules ignore it.

After Phase 1, mochi nags on any site. It is still block-level, still Lua-only, and still
correct.

**Phase 2 — add Harper as the span tier.**

- Add a background service worker. Copy `packages/chrome-plugin/src/manifest.ts`'s CSP
  builder almost verbatim: `script-src 'self' 'wasm-unsafe-eval'` under
  `extension_pages`, `.wasm` as a `web_accessible_resource`, 400 ms keep-alive (§4.1).
  **Do not put the WASM in the content script** — the whole point of Harper's design is
  that the service worker's CSP is yours and the host page's is not.
- Use `WorkerLinter`, never `LocalLinter`. Remember `lint.span()` is a **method**
  returning **character** indices, not a property, and not byte offsets.
- Author `mochi.weirpack` from `Lexicon.stadium` and `Lexicon.inflated`, with the existing
  `rules_spec.lua` cases converted to inline `test`/`allows`. Load it via
  `loadWeirpackFromBlob()` and **fail loudly on returned test failures** — that is the
  same instinct as `content.js`'s "lost" message versus a silently empty draft.
- Turn `SpellCheck` **off** by default. mochi is not a grammar checker and the existing
  `docs/research.md` is right that it must not drift into being one. Harper is here for
  POS-aware style matching, not spelling.
- Delete `Rules.adverbs`, `Rules.passive`, `Rules.inflated`, `Rules.stadium` from
  `rules.lua` once the Weirpack passes on real drafts. Keep `Lexicon` — the tables are the
  content.

**Phase 3 — span-accurate underlines.**

- For contenteditable: **CSS Custom Highlight API with `StaticRange`** (§2.6), feature-
  detected on *both* `CSS.highlights` and `CSS.supports('selector(::highlight(x))')`
  because Firefox 140–148 registers highlights that never paint. Fall back to
  absolutely-positioned boxes.
- For textarea/input: Harper's `TextFieldRange` mirror (§2.4), with `direction`,
  `textAlign`, `textIndent`, `wordSpacing` and `tabSize` added back to its 17-property
  list.
- Position underlines **relative to the field**, not the viewport, so scroll only moves
  one container (§2.8). Batch all reads in one `requestAnimationFrame`, with a `Set` of
  pending underlines — the exact shape that gave Grammarly −50% input latency.
- Treat `rects.length === 0` as "not rendered", never "at 0,0".

Realistically most of this is `packages/lint-framework/src/lint/` used as-is. It is
Apache-2.0, it solves §2 completely, and it is already proven on Substack. Vendoring it is
a better use of the time than reimplementing `computeLintBoxes`.

**Phase 4 — decide whether to draw the document tier at all.**

Probably not, and that is the interesting answer. Grammarly's underline layer carries
everything and its card carries one thing. mochi's split can be cleaner: **Harper spans
get underlines; document findings get the pet.** "This paragraph runs seven sentences"
does not want a squiggle — it wants mochi to say it. Keep `paintMarks`'s block-level rule
for structural findings if it earns its place, but do not promote document findings into
the span layer just because the span layer now exists.

### Where the pet fits

**The pet is the card.** That is the whole differentiation, and it should be stated as a
design rule rather than left implicit.

Grammarly's extension shows one suggestion at a time behind a click, because a card in a
text field is intrusive and the full list is paywalled. mochi already has something
better: a character with a bubble, three timing modes, and a cooldown — outside the page,
so it costs the editor no z-index, no hit-testing, and no stacking-context risk (§1.7).

So the division of labour after Phase 3:

- **Underlines** — passive, silent, span-accurate, never interrupt. Harper's tier. They
  are the ambient signal; the user consults them.
- **The pet** — speaks structural findings only, on `nag.lua`'s existing schedule. The
  interrupting signal, and rationed.
- **Click the pet** — `Nag.onDemand` already does the right thing: it answers a direct
  question even if it just said the same thing, because silence would read as broken.

One thing to protect: `nag.lua`'s `MAX_LINES = 4` and the signature check exist so the pet
does not become a wall. Adding Harper multiplies the raw finding count by a large factor —
hundreds of built-in rules against four hand-written ones. **Harper's output must not
reach `Nag.consider` at all.** If it does, mochi becomes exactly the thing it was designed
against: a checker that repeats itself and gets switched off. Span findings go to the
overlay and stop there.

### What not to do

- **Do not use write-better** (§4.2) — no license at all, so it is legally unusable, and
  its DOM-injection highlighting is the specific anti-pattern Grammarly documented
  abandoning. It should be removed from `docs/research.md`'s reference table.
- **Do not port the document rules to JS.** They are tested, working, and in the right
  place.
- **Do not add a server tier.** Grammarly is moving *off* one (§3.4); starting one in 2026
  is designing toward where they were.
- **Do not build the write path.** §1.5 is unambiguous: underlines are safe, applying
  edits against DOM coordinates is where every remaining Grammarly bug lives, and
  `EditContext` adoption is closing that door entirely. mochi critiques; the writer edits.
  That limitation is a feature, and it is worth saying so out loud rather than treating it
  as a gap to fill later.
